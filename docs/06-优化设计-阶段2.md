# 阶段 2 技术设计：四项新增功能 + 三个既有缺陷

> 状态：**仅设计，未实施**。所有条目都要等确认后再动代码。
> 基线：`v1.2.0`（`f4ad7d3`），审查分支 `opt/v1.3`。
> 冻结范围：`hermesfix/src/`、`iloader-main/vendor/`、`apple-codesign/`、`patches/` 一律不碰。

先说结论：**四项功能里，有三项不需要改 Rust 就能做。** 唯一真正受限的是「验证码送达状态」——
引擎只输出文本，不输出「Apple 已接受请求」这种结构化状态，硬做只能靠猜。这一点下面单独说明。

## A. 受信任手机号选择 + 验证码状态

### A.1 现状（已核对代码，非推测）

引擎 `hermesfix/src/main.rs` 第 151–197 行的 2FA 回调，每次被调用都会往 **stderr** 打这些：

```
[!] Apple reported: {last_error}                    ← 有错才打
    sms supported : {true|false}
    trusted numbers: <none reported>                ← 没有号码时
    trusted number: id={n} {带区号的完整号码} (***{后两位}) push={true|false}
    preselected   : id={n}                          ← Apple 指定了默认号码时
    input: 6-digit code | push | resend | sms [id] | abort
```

然后往 **stdout** 打 `Two-factor code: `（不带换行），阻塞等 stdin。

stdin 接受的词（第 174–196 行）：

| 输入 | 效果 |
| --- | --- |
| `push` / `device` | SendToDevices |
| 空 / `resend` | ResendCode |
| `sms` / `sms 3` | SendSms(id=3)，不带 id 时用 preselected 或第一个 |
| `abort` / `q` | Abort |
| 任意其他（含数字） | SubmitCode(只保留数字) |

**所以号码列表、号码 id、能否短信、默认号码，GUI 全都能拿到，不需要改 Rust。**

### A.2 方案

**新增 `gui/TwoFactorPanel.cs`（约 120 行）**

只做三件事，不碰现有 `Send()` / `SubmitCurrent()`：

1. `static IReadOnlyList<TrustedNumber> Parse(IEnumerable<string> stderrLines)`
   识别 `trusted number:` 行，抽出 `id` / `push` / 掩码号码。
   **掩码直接用引擎给的 `(***NN)` 后两位，不自己截完整号码**——引擎已经算好了，重复截容易截错。
2. 状态机 `Idle → Sent → WaitingCode → Failed`，驱动按钮可用性。
3. 把 `sms {id}` 交给现有的 `Send()`，不自己写 stdin。

**改 `gui/MainWindow.xaml`（约 20 行）**

在 2FA 栏 `TwoFaInput` 下方加一个 `ItemsControl`（初始 `Visibility="Collapsed"`），每项一个可点选的小胶囊：`***88` / `***12`。点中后把「短信」按钮的语义变成「发到这个号」。

**改 `gui/MainWindow.xaml.cs`（约 40 行，只加不改）**

- `OnChunk` 的 stderr 分支里，把行喂给 `TwoFactorPanel.Parse`
- `OnPrompt(PromptKind.Code)` 时刷新号码胶囊
- 新增一个 `SendToNumber(uint id)`，内部仍是 `Send($"sms {id}")`

### A.3 不改什么

- `Send()` 的写 stdin 逻辑
- `SubmitCurrent()` 的验证码提取
- `OnPrompt` 对三种 PromptKind 的既有分支
- 引擎的 stdin 协议

### A.4 风险

| 风险 | 说明 | 处理 |
| --- | --- | --- |
| 回调可能被多次调用 | 每次都会重打列表，若追加会越堆越多 | 每次 `OnPrompt` 先清空再填 |
| `sms supported: false` | 号码列出来了，但 Apple 说不能发短信 | 胶囊置灰，悬浮提示「Apple 未开放短信」 |
| 完整号码进日志 | 见下方缺陷 ③，**这是现有行为**，不是新功能引入的 | 与缺陷 ③ 一起修 |
| `unknown: true` | 引擎没有单独打印这个字段 | 只能靠「sms supported」和号码列表推断，**不额外造状态** |

### A.5 关于「验证码发送状态」

用户要求区分这六种：已提交请求 / Apple 已接受 / 等待输入 / 请求失败 / 验证码错误 / 用户中止。

**能做到的：**

| 状态 | 依据 | 可靠性 |
| --- | --- | --- |
| 已提交请求 | GUI 自己知道刚写了 stdin | 确定 |
| 等待输入 | 引擎再次打出 `Two-factor code: ` | 确定 |
| 请求失败 | stderr 出现 `[!] Apple reported:` 或 `login failed` | 确定 |
| 验证码错误 | 同上，错误文本含 code/incorrect 类字样 | 高，但依赖错误文案，Apple 改词就会失效 |
| 用户中止 | 自己点了「中止」 | 确定 |
| **Apple 已接受请求** | **引擎没有输出这个信号** | **做不到** |

所以不做「已成功发送」的提示，改为：点完按钮显示「已请求，等待 Apple 回应」，收到下一次 `Two-factor code: ` 才算完成一轮。
这正好符合用户的要求——不因为写了 `push` 就说「已发送成功」。

### A.6 测试（不需要真实账号）

扩展 `gui/tests/fake-engine/Program.cs`，用环境变量选择剧本：

| 剧本 | 输出序列 |
| --- | --- |
| `FE_SCRIPT=ok` | 列表 → 提示 → 收码 → `login ok` |
| `FE_SCRIPT=nosms` | `sms supported : false` + 两个号 |
| `FE_SCRIPT=none` | `trusted numbers: <none reported>` |
| `FE_SCRIPT=unknown` | 只有 `input: ...`，无列表 |
| `FE_SCRIPT=wrongcode` | 收码后打 `[!] Apple reported: incorrect` 再重提示 |
| `FE_SCRIPT=abort` | 收 `abort` 后退出码 0 但不打 `login ok` |
| `FE_SCRIPT=split` | 把 `Two-factor code: ` 拆成两次 write，验证尾串匹配不会漏 |

**顺带要修测试替身的偏差**（现在就有，不是新问题）：`fake-engine` 打的是
`(***88)` 前面带 `+86 138****8888`（已掩码），而真实引擎打的是**完整号码**。
测试替身比真实情况"更干净"，容易让隐私问题在测试里看不出来。

## B. IPA 在线版本检查

### B.1 现状

`gui/EnvCheck.cs` 第 87–93 行把 `KnownIpaSize` / `KnownIpaSha` 写死为 1.5.1 的指纹。
不一致时给 `Warn`，不阻止签名。**没有任何联网检查。**

### B.2 方案

**新增 `gui/ReleaseCheck.cs`（约 100 行，纯只读）**

```
GET https://api.github.com/repos/pookjw/HermesEnabler/releases/latest
```

- 用 `HttpClient`，`Timeout = 6s`，只发一次，失败就静默返回 `Unavailable`
- 解析 `tag_name` / `html_url` / `published_at` / `body` 前 200 字
- **不下载、不替换、不校验上游哈希**（上游 release 不提供 sha256）
- 结果缓存到内存 + 8 小时内不再请求（避免每次启动都打 GitHub）

**`gui/EnvCheck.cs` 加第 7 项检查**

| 项 | 状态 | 文案 |
| --- | --- | --- |
| 上游版本 | `Ok` | 上游最新 1.5.4，你用的是 1.5.1 |
| | `Info` | 已是最新（1.5.4） |
| | `Warn` | 查不到（离线 / 限流）——**不影响签名** |

注意：`CheckState` 现有四档（Ok/Warn/Fail/Info）够用，不新增枚举。

### B.3 明确不做

- 不自动下载
- 不覆盖 `ipa/` 里的文件
- 不因为版本旧就拦签名
- **不把未实测的新版本标成「兼容」**——只显示版本号差异，兼容性一栏永远写「未验证」

### B.4 风险

| 风险 | 处理 |
| --- | --- |
| 无网络时启动变慢 | 6 秒超时 + 后台线程，自检界面先出结果、这一项后填 |
| GitHub 限流（未认证 60 次/时） | 8 小时缓存 + 失败静默 |
| 用户误以为新版必须升 | 文案写死「能签，但本项目未实测」 |

### B.5 测试

- 单元测试：喂构造的 JSON（有 release / 空 / 404 / 超时）
- 无法离线验证真实 API 时，如实标注「仅用构造数据验证」

## C. 引擎版本提示

### C.1 现状

`MainWindow.ResolveEngine()` 第 131–143 行：

```csharp
if (!string.IsNullOrWhiteSpace(remembered) && File.Exists(remembered))
    return remembered;          // ← 手动换过的引擎优先，可以盖掉内嵌的
var embedded = Engine.Resolve();
```

`UpdateEngineText()` 只显示路径，**不显示版本，也不说明这是内嵌的还是外部的**。
用户看到一行路径，无从判断自己是不是在用旧引擎。

### C.2 方案

**`gui/Engine.cs` 加两个只读方法（不改 `ExtractEmbedded` 的任何行为）**

```csharp
public static string Describe(string path)      // "内嵌 v1.2.0 · 700444d3" / "外部 · 未校验"
public static bool IsEmbeddedCopy(string path)  // 路径是否等于当前程序释放出的那个
```

**`UpdateEngineText()` 改成三段式**

```
签名引擎：内嵌 v1.2.0 · 700444d3 · C:\...\v1.2.0.0\hermesfix.exe
```

外部引擎时标红并加一句「外部引擎，未经验证，可能不是本仓库版本」。

### C.3 风险

低。只是把已有信息（程序集版本 + 已知哈希）显示出来。
唯一要小心的是 `EngineText` 有 `MaxWidth="420"` + 省略号，文案变长会被截——需要同时把 `MaxWidth` 提到 520 或允许换行。

## D. 安全日志导出

### D.1 现状

- `_logAll` 攒了**全部** stdout + stderr 原文
- `OpenFolder_Click` 打开的是日志目录，日志文件由引擎自己写
- **没有任何脱敏，也没有导出功能**——用户想反馈问题，只能自己复制整段日志

### D.2 方案

**新增 `gui/LogRedactor.cs`（约 80 行，纯函数）**

| 目标 | 规则 |
| --- | --- |
| Apple ID 邮箱 | `[\w.+-]+@[\w.-]+\.\w+` → 保留首字符 + `***@域名` |
| 完整手机号 | `\+?\d[\d\s-]{8,}\d` 且长度 ≥ 9 → `***` + 后两位 |
| 6 位验证码 | 紧跟在 `Two-factor code:` 后的数字 / 长度恰为 6 且上下文含 code → `••••••` |
| UDID / 序列号 | `\b[0-9a-f]{24,40}\b`（大小写不敏感）→ 前 4 位 + `…` |
| 路径里的用户名 | `C:\Users\[^\\]+` → `C:\Users\<user>` |

**UI 入口**：2FA 栏旁边或日志标题行加一个「导出脱敏日志」，`SaveFileDialog` 存 `.txt`。
**不默认上传任何地方**，只落本地文件。

### D.3 风险

| 风险 | 处理 |
| --- | --- |
| 正则误伤正常文本 | 每条规则配单元测试，用真实日志样本跑一遍，人工比对 diff |
| 漏掉新的敏感格式 | 导出文件头写一行「已自动脱敏，仍建议自行检查」 |
| 用户以为导出=安全 | 同上，不承诺「绝对干净」 |

### D.4 测试

拿本机现有日志（`bin/hermesfix.log`，含真实 Team ID）做样本，跑脱敏后断言：
- 不含 40 位 hex
- 不含 `@` 后的完整本地部分
- 不含完整 11 位数字串
- 有效信息（阶段标记、错误码）仍在

# 顺手查出的三个既有缺陷

以下都不是新功能，是审查时在现有代码里看到的。**按规则只记录，不擅自修。**

## 缺陷 ①：清空日志会抹掉进度判定的依据（确认存在）

`ScanSteps()` 第 394 行每次都用 `_logAll.ToString()` **全量重扫**，
而 `ClearLog_Click()` 第 250–254 行会 `_logAll.Clear()`。

后果链条：

1. 跑到 `login ok`，chip 1 变绿
2. 用户点「清空」（只是想清理屏幕）
3. 引擎继续输出 `[2/4]` → `MarkStep(2)` 触发
4. `MarkStep` 循环重绘**所有** chip，逐个查 `_logAll`
5. `_logAll` 里已经没有 `login ok` 了 → chip 1 **退回灰色**

**修法（阶段 3，约 15 行）**：把「已完成到第几步」存成独立字段，`ClearLog_Click` 不碰它；
`ScanSteps` 改成只看新增的一段（增量扫描），顺带解决下面的性能问题。

## 缺陷 ②：内嵌引擎缓存只信任标记文件，不校验实际内容

`Engine.cs` 第 38–44 行：

```csharp
if (File.Exists(target)
    && new FileInfo(target).Length == stream.Length   // 只比大小
    && File.Exists(marker)
    && File.ReadAllText(marker).Trim() == hash)       // 只信标记
```

只要**替换后的 exe 大小一致**且 `.sha256` 标记文件没被动，就会直接使用被替换的引擎。
本工具要拿 Apple ID 密码，这条路径值得收紧。

**修法（阶段 3，约 3 行）**：把大小比较换成 `HashFile(target) == hash`。
代价是每次启动多算一次 26 MB 哈希（实测约 80–120 ms），换来「磁盘上那份一定等于内嵌那份」。

## 缺陷 ③：完整手机号已经进了日志（隐私）

`hermesfix/src/main.rs` 第 162 行打的是 `n.number_with_dial_code` —— **完整号码带国际区号**。
这个走 stderr → `AppendLog` → `_logAll` → 日志文件。用户如果把日志发给别人排错，
受信任手机号就跟着出去了。

**这条不能靠改 Rust 修**（Rust 冻结）。只能在 GUI 侧做：`AppendLog` 入口先过一遍 `LogRedactor`，
或者专门对 `trusted number:` 行做掩码再落日志。引擎那边照打不误，用户屏幕上和文件里都是掩码。

# 实施顺序建议

| 顺序 | 内容 | 依赖 | 风险 |
| --- | --- | --- | --- |
| 1 | 缺陷 ② 引擎哈希校验（3 行） | 无 | 极低 |
| 2 | 缺陷 ① 进度状态与日志解耦 | 无 | 低 |
| 3 | 缺陷 ③ 日志脱敏（就是功能 D 的 `LogRedactor`） | 无 | 低 |
| 4 | 功能 C 引擎版本提示 | 无 | 低 |
| 5 | 功能 A 受信任号码选择 | `LogRedactor`（号码不回显） | 中 |
| 6 | 功能 B 上游版本检查 | 无 | 中 |
| 7 | **不动**：验证码「已送达」判定 | 需要改 Rust | — |

先做 1–4，风险都很低且互相独立；A 放在脱敏之后，避免新功能顺手把号码写进日志。

# 需要你确认的点

1. **A 的交互形态**：号码做成「点一下就把短信按钮变成发给它」，还是「下拉选一个号，再点短信」？前者少一次点击，后者更不容易误触。
2. **B 的联网行为**：允许程序**启动时自动**查一次上游版本（8 小时缓存），还是只在用户点「环境自检」时查？
3. **D 的入口位置**：导出脱敏日志放在日志标题行（跟「清空」并排），还是放在底栏？
4. **缺陷 ①②③ 是否一并授权**在阶段 3 处理。②只有 3 行，但改了就是动了 `Engine.cs`（冻结清单内）——需要你明确点头。
