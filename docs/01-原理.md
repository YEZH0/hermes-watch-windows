# 01 · 原理：为什么免费账号能行，而工具不行

## 1. iOS 侧载的 entitlements 从哪来

一条很容易被误解的链路：

```
Apple Developer API                 本地签名                    设备运行
─────────────────            ────────────────────       ─────────────────
App ID (bundle id)    ──►    Provisioning Profile   ──►   entitlements
  + 能力位 (features)            (Apple 签发)              写进 Mach-O
  + App Group 分配                    │
                                      └──► codesign 只负责"照抄"
```

关键点：**签名工具不会凭空造权限。**
`apple-codesign` 做的事是"把 Profile 里的 `Entitlements` 字典写进二进制的签名区"。
如果 Profile 里没有 `com.apple.security.application-groups`，本地再怎么改代码都没用。

所以问题只能出在两处：

- Apple 账号没有该能力（→ 需要换账号）
- **工具没去 Apple 那边申请该能力**（→ 改工具）✅ 本例属于这一类

## 2. App Groups 在 Developer API 里是三个动作

| 步骤 | API | 说明 |
| --- | --- | --- |
| ① 开通能力位 | `updateAppId`，`features: { APG3427HIY: true }` | 给 App ID 打上 App Groups 能力标记 |
| ② 创建/找到 Group | `addApplicationGroup` / `listApplicationGroups` | Group 标识形如 `group.<bundle-prefix>.<TEAMID>` |
| ③ 分配给 App ID | `assignApplicationGroupToAppId` | 分配之后，下次生成的 Profile 才带这个 entitlement |

三步缺任何一步，Profile 里都不会出现 `application-groups`。

## 3. watchOS App 是"另一个 App"，且需要平台标记

一个带表盘的 IPA 里有**两套签名对象**：

```
Payload/
└─ HermesCompanion.app/                     ← iPhone App
   ├─ embedded.mobileprovision               (profile A)
   ├─ HermesCompanion                        (Mach-O A)
   └─ Watch/
      └─ HermesEnabler2.app/                ← watchOS App（独立 bundle id）
         ├─ embedded.mobileprovision         (profile B)  ← 单独的 App ID
         └─ HermesEnabler2                   (Mach-O B)
```

watchOS 的 App ID 在 Apple 侧属于另一个"平台命名空间"。调用 Developer API 时必须在请求体里带：

```json
{ "DTDK_Platform": "watchos" }
```

否则 Apple 按 iOS 命名空间去找，找不到这个 App ID，`updateAppId` 直接失败。
isideload 上游已经有 `DeveloperDeviceType::Watchos` 和 `apply_platform_to_body()`，能力是齐的——只是**没在这条路径上用**。

## 4. 上游 bug 到底在哪

`iloader-main/vendor/isideload/isideload/src/sideload/sideloader.rs`，签名前会为 IPA 里每个 App ID 补权限：

```rust
for app_id in app_ids.iter_mut() {
    if watch_bundle_ids.contains(&app_id.identifier) {
        continue;                       // ← 手表 App ID 被整个跳过
    }
    app_id.ensure_group_feature(&mut self.dev_session, &team).await?;   // ① 能力位
    self.dev_session.assign_app_group(&team, &app_group, app_id, None).await?;  // ③ 分配
    ...
}
```

推测上游这么写的原因：早期 watch App ID 走带 `DTDK_Platform` 的路径会报错，于是干脆跳过。
代价就是——**iPhone App 拿到了 Group，手表 App 没拿到**，运行时手表端 `GroupContainers` 为空，表盘一读共享容器就崩。

## 5. 修复

```rust
for app_id in app_ids.iter_mut() {
    let device_type = if watch_bundle_ids.contains(&app_id.identifier) {
        Some(DeveloperDeviceType::Watchos)      // 手表 → 带平台标记
    } else {
        None                                     // iPhone → 保持原行为
    };

    app_id
        .ensure_group_feature(&mut self.dev_session, &team, device_type.clone())
        .await?;
    self.dev_session
        .assign_app_group(&team, &app_group, app_id, device_type)
        .await?;
    ...
}
```

单 hunk、不新增依赖、不改函数签名——因为 `ensure_group_feature` 与 `assign_app_group` 上游本来就接受 `impl Into<Option<DeveloperDeviceType>>`。
补丁见 [`patches/0001-isideload-watch-appgroup.patch`](../patches/0001-isideload-watch-appgroup.patch)。

## 6. 免费 Apple ID 的真实边界

实测结论：

| 能力 | 免费个人团队 |
| --- | --- |
| 创建 App ID（含 watchOS） | ✅ |
| 开通 App Groups（`APG3427HIY`） | ✅ |
| 创建 `group.*` 并分配 | ✅ |
| 生成带 `application-groups` 的 Profile | ✅ |
| 同时有效证书数 | 3 张 |
| Profile 有效期 | **7 天** |
| 推送通知 / CarPlay 等 | ❌（与本任务无关） |

也就是说，这条路上唯一需要反复处理的是 **7 天到期**，不是权限。
