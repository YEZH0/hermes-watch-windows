# 02 · 构建：为什么这么绕，以及每一步解决什么

目标产物：`hermesfix.exe` —— 一个把 `isideload` 的登录、签名、安装能力串起来的 CLI。
真正的难点不在 Rust 代码（287 行），而在 **Windows 上把它编出来**。

---

## 1. 先决条件

| 项 | 本机实测值 |
| --- | --- |
| Rust | `rustc 1.99.1`，target `x86_64-pc-windows-gnu` |
| C 工具链 | MinGW-w64（`x86_64-w64-mingw32-gcc` / `ar` / `dlltool`） |
| 汇编器 | NASM（`ring` 需要） |
| 额外运行时 | 无（成品是单个 exe） |

## 2. 为什么用 GNU 而不是 MSVC

上游推荐 MSVC，但本机实测**不可行**：

| 检查 | 结果 |
| --- | --- |
| `vswhere -requires VC.Tools` | 空 —— 没装 MSVC 生成工具 |
| Windows SDK | 无 |
| `cl.exe` | 不存在 |
| iloader 构建链 | 还需要 **Bun**（前端） |
| 补装体积 | **5–6 GB** |
| 实测下载速度 | ≈ 135 KB/s → 数小时 |

于是走 GNU。代价是要自己处理三个 Windows 特有的坑，见下。

## 3. 坑一：中文用户名 + binutils = 路径乱码（最费时）

**现象**：`cargo build` 在任何链接/汇编步骤失败，报错里路径长这样：

```
C:\Users\ÕÅÈý\.cargo\...        ← 本该是 C:\Users\张三
```

**根因**：binutils 的 Windows 移植版用 ANSI 代码页（CP936/CP1252）处理路径，不认 UTF-16。
`rustc` 会在 `-L` / `-o` 里塞进绝对路径，一旦路径含中文就不可逆地损坏。

**试过但无效的方案**：

| 方案 | 为什么不行 |
| --- | --- |
| `subst W: C:\Users\张三` | 编译期能过，但 rustc 内部仍会 canonicalize 回真实路径；换盘符后 cargo 缓存全失效 |
| `RUSTUP_HOME` 指到 ASCII 路径 | 同上，且触发**全量重编**，把已经编好的 800 MB 依赖作废 |
| 8.3 短名（`Ò¶Ö¾~1`） | 父目录仍是中文，binutils 依旧乱码 |

**最终解法**：把整个 toolchain 物理复制到纯 ASCII 路径，用 `RUSTC` 指向它。

```bash
robocopy "C:\Users\张三\.rustup\toolchains\stable-x86_64-pc-windows-gnu" "C:\rt" /E /NFL /NDL
export RUSTC="C:/rt/bin/rustc.exe"
```

`C:\rt` 约 841 MB。**只有这一招真正生效。**

> 注意：这条路径必须和 `cargo` 是同一条工具链。设置 `RUSTC` 后 cargo 会以它为准，
> 不再读 rustup 的默认 toolchain，所以不需要也不应该改 `rust-toolchain.toml`。

## 4. 坑二：依赖不是 crates.io 的

`isideload` 原本依赖 `apple-codesign` 的 **git 源**（`nab138/apple-crates`），
而该 commit 里真正的包在 `apple-codesign-quick/` 子目录下，`[patch]` 对 git 源**不生效**。

处理：

1. 把 `apple-codesign-quick/` 复制成仓库内的 `apple-codesign/`
2. 它的 `Cargo.toml` 里 `workspace = true` 全部展开成具体版本
   （`plist="1"`、`thiserror="2"`、`sha1="0.11.0"`、`sha2="0.11.0"`）
3. `isideload/Cargo.toml` 改成路径依赖：

```toml
apple-codesign = { path = "../../../../apple-codesign", version = "0.1.0", package = "apple-codesign" }
```

改完 `Cargo.lock` 里 **0 个 git 源**，从此 `--offline` 也能复现。

## 5. 坑三：cc-rs / ring / libgcc_eh

| 报错 | 原因 | 处理 |
| --- | --- | --- |
| `failed to find tool "gcc"` | cc-rs 找不到编译器 | `export CC_x86_64_pc_windows_gnu=<abs>/gcc.exe` |
| `error calling dlltool 'dlltool.exe'` | rustc 不知 dlltool 在哪 | `RUSTFLAGS="-C dlltool=<abs>/dlltool.exe"` |
| `cannot find -lgcc_eh` | GCC 16 把 libgcc_eh 并进 libgcc | `ar crs <libdir>/libgcc_eh.a`（空占位即可） |
| ring 编译时 nasm 找不到 | build.rs 硬编码 `./target/tools/windows/nasm/nasm` | 把 nasm 复制到该路径 |

## 6. 编译提速

`isideload` 体量大、模板多，release 优化要花很久，而本工具一生只签几次。
在 `Cargo.toml` 里单独降级：

```toml
[profile.release.package.isideload]
opt-level = 0
```

增量编译（只改 `main.rs`）实测 **12.56 秒**。

## 7. 完整命令

```bash
cd hermesfix

export RUSTC="C:/rt/bin/rustc.exe"                 # 决定性：纯 ASCII 路径
export CARGO_HOME="C:/Users/<you>/.cargo"
export PATH="/c/Dev/w64devkit/bin:$CARGO_HOME/bin:$PATH"

export CC_x86_64_pc_windows_gnu="/c/Dev/w64devkit/bin/x86_64-w64-mingw32-gcc.exe"
export AR_x86_64_pc_windows_gnu="/c/Dev/w64devkit/bin/x86_64-w64-mingw32-ar.exe"
export RUSTFLAGS="-C dlltool=/c/Dev/w64devkit/bin/x86_64-w64-mingw32-dlltool.exe"

cargo build --release --offline
```

封装版见 [`scripts/build-windows-gnu.sh`](../scripts/build-windows-gnu.sh)。

## 8. 编不出来时的排查顺序

1. **先看报错里的路径有没有乱码** —— 有就是中文路径问题，回到第 3 节
2. `RUSTC` 指的工具链是否真的存在：`"$RUSTC" --version`
3. 残留 cargo 进程占锁：`taskkill /F /IM cargo.exe`
4. `--offline` 失败说明 registry 缓存不全，去掉 `--offline` 联网补一次
5. `ring` 相关失败 90% 是 nasm 路径问题
