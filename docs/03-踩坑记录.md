# 03 · 踩坑记录：症状 → 真实原因 → 处理

按"最容易误判"排序。**加粗的是当时判断错的地方。**

---

## A. 权限类

### A1. 手表报 *An App Group ID may be missing*

| | |
| --- | --- |
| **误判** | 免费 Apple ID 没有 App Groups 权限，必须买 99 美元开发者账号 |
| **真实原因** | isideload 对 watchOS 的 App ID 直接 `continue`，从未申请能力位、从未分配 Group |
| **证据** | iPhone 端 profile `AppGroups: PRESENT`；手表端 `MISSING` —— 同一账号、同一 IPA，差异只在代码路径 |
| **处理** | 打补丁让 watch App ID 也走 `ensure_group_feature` + `assign_app_group`，见 [docs/01](01-原理.md) |

**这件事的教训**：遇到"权限缺失"，先分清是"账号没有"还是"工具没要"。
判据很简单——同一账号下另一个 target 有没有。有，就是工具的问题。

### A2. 手表端 GroupContainers 为空

是 A1 的运行时表现，不是独立问题。修好 A1 即可。

## B. 登录类

### B1. `Auth error -80045`

| | |
| --- | --- |
| **真实原因** | anisette 数据与 `client-info` 的来源不一致。Apple 从 2026-10 起强制校验两者必须来自同一实现 |
| **处理** | 统一使用 `RemoteV3AnisetteProvider`，指向同一个 anisette 服务（`https://ani.jkcoxson.com`），serial 固定 `"0"` |
| **不要做** | 不要混用本地 anisette 与远程 anisette；不要重用别的工具存的 anisette 状态 |

### B2. `... is not provisioned for this server (-45061)`

| | |
| --- | --- |
| **真实原因** | 同一账号在别处（如另一台机器的 iLoader）留下了不一致的 anisette provisioning，服务端拒绝 |
| **处理** | 保持 keyring service 与 machine name 与 iLoader **完全一致**，复用它的状态而不是新建 |
| **关键常量** | `SERVICE=io.github.andreysemjonov.iloader`、`MACHINE=iloader` |

本仓库的 `main.rs` 就是靠这两个常量做到"零新增证书"：

```rust
const SERVICE: &str = "io.github.andreysemjonov.iloader";
const MACHINE: &str = "iloader";
```

私钥在 Windows 凭据管理器里的条目名是 `sha256(lowercase(email))/key.<SERVICE>`。
启动器会先算 `sha256(email)` 跟已知值比对，命中就说明"将复用现有证书"。

### B3. 一直收不到验证码

| | |
| --- | --- |
| **误判** | 以为 Apple 会发短信，等了十分钟 |
| **真实原因** | **Apple 默认把 6 位码推送到受信任设备的弹窗里，不发短信** |
| **处理** | 解锁 iPhone/手表 → 等"Apple ID 登录"弹窗 → 点允许 → 码显示在那台设备上 |
| **兜底** | 在验证码提示处输入 `push` / `resend` / `sms` / `sms 2` / `abort` |

这一条是本项目里唯一"用户以为坏了、其实没坏"的问题。
启动器已经把这段说明前置打印，避免再踩。

## C. 设备连接类

### C1. 装完 iPhone 端后设备从 usbmux 掉线（设备数 0）

| | |
| --- | --- |
| **真实原因** | 安装过程中 iOS 重建了 app 容器，usbmux 会话被回收 |
| **处理** | 拔插数据线，重新解锁并信任；无需重新配对 |
| **注意** | 此时**不要**判定为安装失败——`InstallComplete` 已经打印过就说明装上了 |

### C2. 手表开发者模式打不开

| | |
| --- | --- |
| **真实原因** | 手表没有 USB，所有命令必须经 iPhone 的 `CompanionProxyService` 代理 |
| **前置条件** | 手表已配对、与 iPhone 同一 Wi-Fi、**放在充电器上** |
| **处理** | 用 `pymobiledevice3` 走 companion proxy 通道，最终下发 `com.apple.amfi.lockdown {"action":0}` |
| **验证** | 读回 `developer_mode: true` 才算成功，不要凭"设置里看到开关"判断 |

### C3. Watch 安装失败，日志只有 `Failed to pair with the Apple Watch through companion proxy`

| | |
| --- | --- |
| **真实原因** | 最常见的是**手表锁屏**。`LockdownClient::pair()` 走 companion proxy 转发到手表 lockdown 端口，表盘锁着时 watchOS 立刻回 `PasswordProtected`，外层只包了一句人话，看不到这个变体名 |
| **如何一眼确认** | 不要在字符串里找 `locked`——`PasswordProtected` 与 `DeviceLocked` 是两个不同变体，按类型 downcast `IdeviceError` 才不会分错 |
| **处理** | 抬腕输入手表密码解锁。**解锁之前重试、重新登录、重新签名都没有任何用** |
| **其他同族错误** | `PairingDialogResponsePending` = 手表上「信任」弹窗没点；`UserDeniedPairing` = 点了不信任；`IXErrorDomain Code=48` = watchOS 安装协调器被上一个进程占着，等 30 秒 |
| **注意** | 手表阶段失败**不等于**前面的步骤白做了。签名产物可以复用，见 [教程 §8.2](05-使用教程.md) |

### C4. 设备端只回一句「无法验证此 App 的完整性」

| | |
| --- | --- |
| **真实原因** | profile 与 bundle 对不上、目标设备不在 `ProvisionedDevices` 里、或 entitlements 缺 App Group |
| **处理** | 这三条都能**离线**判定。`hermesfix` 在把包交给设备之前先自检一遍，把含糊的设备端报错提前成本地明确结论 |
| **注意** | 判定要保守：只有"必然装不上"才算致命，其余只记日志，别把本来能用的流程挡下来 |

## D. 构建类

见 [docs/02-构建.md](02-构建.md) 第 8 节。最高频的两条：

- 报错路径出现 `Ò¶Ö¾ºê` → 中文路径，必须把 rustc 放到纯 ASCII 目录
- `cargo` 卡住不动 → 有残留进程占锁，`taskkill /F /IM cargo.exe`
- 界面产物**不能**叫 `HermesFix.exe`：Windows 文件名不区分大小写，它和引擎 `hermesfix.exe` 是同一个文件，复制过去会直接把引擎覆盖掉。这就是现在叫 `HermesFixGui.exe` 的原因

## E. 判断失误的通用清单

这次绕远的三个决策，下次可以直接跳过：

1. **"免费账号肯定不行"** —— 没验证就下结论。正确做法是先做一个最小验证：
   用同一账号给 iPhone App 建一个 App Group，看 API 是否 200。
2. **"重编全部依赖更稳"** —— 在中文路径上反复重编，每次都失败在同一处。
   正确做法是先定位**是不是环境问题**，再决定要不要动代码。
3. **"MSVC 更官方所以更好"** —— 官方推荐不等于本机可行。
   先量成本（体积、带宽、额外依赖），再决定，别先下载 5 GB。
